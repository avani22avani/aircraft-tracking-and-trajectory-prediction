4.5 Sequence of Operation 
When the application starts, configuration values are read from environment 
variables. The Flask application creates one preprocessor and one storage object. 
For every dashboard refresh, the browser calls the aircraft API. The backend 
obtains raw or replayed data, preprocesses it, stores it and returns the normalized 
records. The browser then updates markers, route traces, aircraft list and charts. 
This sequence keeps the browser simple and places the core data responsibility in 
Python. 
1. Application starts and prepares output directories. 
2. Data source selects simulation replay or live receiver mode. 
3. Raw records are decoded and cleaned. 
4. Records are normalized into common units. 
5. Storage layer writes meaningful latest and trajectory samples. 
6. API response is sent to the browser. 
7. Dashboard updates markers, list, panels and chart.

4.6 Design Rationale 
A local Flask application was selected because the project needs simple API 
endpoints, not a large enterprise framework. SQLite was selected because it stores 
structured data in one file and is suitable for local academic projects. CSV and 
Excel exports were retained because they make the captured data easy to inspect 
in spreadsheet tools. Leaflet was selected because it is a mature web mapping 
library and works well with marker-based aircraft visualization.

5. CODING 
The implementation is organized into small modules instead of keeping all logic 
in one file. Only the main parts are discussed here, as detailed source code is not 
required in the main body of the report. 
5.1 Backend API 
The Flask application exposes endpoints for live aircraft, training matrix, logging 
status and trajectory export. The /api/aircraft endpoint is the most important 
endpoint because the browser calls it repeatedly to update the live map. 


===== PAGE 27 =====

5.2 Decoder and Preprocessing 
The decoder reads complete frames from the buffer, extracts fields such as ICAO 
address, callsign, altitude, ground speed, heading, latitude and longitude, and 
maintains an aircraft state snapshot. The preprocessor then ensures values use 
consistent units: altitude in millimetres, speed in centimetres per second and 
heading in degrees multiplied by 100. 
5.3 Storage and Export 
The storage layer writes meaningful trajectory samples instead of saving every 
repeated value. This reduces duplication while retaining useful movement 
information. It also writes CSV files and ICAO-wise Excel workbooks so that the 
data can be reviewed outside the dashboard. 
5.4 User Interface 
The dashboard uses Leaflet for map visualization and Chart.js for the altitude 
chart. Aircraft markers show callsigns and heading direction, while the lower 
panel displays selected aircraft details, route estimate and altitude history. The 
interface is intentionally compact so that tracking information remains visible on 
one screen. 
5.5 Error Handling and Data Quality 
The implementation includes several small safeguards to improve data quality. 
The data source filters records with zero latitude and longitude, the decoder 
ignores incomplete or invalid frames, and the preprocessor applies default values 
when fields are missing. The storage layer uses thresholds for time, distance, 
altitude, heading and speed changes so that the database does not fill with repeated 
identical samples.

7. USER INTERFACES 
The web interface is built as a single-page dashboard. The top area contains the 
project title, search box and live status counters. The left panel lists live traffic. 
The central map displays aircraft markers with heading rotation and route traces. 
The bottom panel displays flight, aircraft and route information for the selected 
aircraft along with an altitude chart. 
• Search by callsign or ICAO address. 
• Click an aircraft marker or list item to view details. 
• Zoom and center controls for map navigation. 
• Route trace and estimated movement line for selected aircraft. 
• Altitude chart for recently observed points. 
7.1 Interface Layout 
The layout is divided into a top status bar, a traffic list, a central map and a bottom 
details panel. This layout was chosen because it keeps the map visible while still 
allowing the user to inspect individual aircraft data. On smaller screens, the traffic 
list is hidden and the bottom panel receives more vertical space.

7.2 Interface Controls 
• The search box filters the visible aircraft list and map layers. 
• The zoom buttons call Leaflet zoom functions. 
• The center button returns the map to the default India-sector view. 
• Tabs separate flight, aircraft and route details so the lower panel remains 
readable. 
• The altitude chart updates for the selected aircraft only. 
8. CONCLUSION AND FUTURE SCOPE 
8.1 Conclusion 
The ADS-B live tracker successfully converts Pingstation aircraft data into 
structured and readable information. It provides a complete local pipeline from 
raw data input to browser visualization and historical storage. The system 
demonstrates practical use of Python, Flask, SQLite and JavaScript mapping tools 
for a real-time tracking problem. 
8.2 Future Scope 
• Testing with a continuous live receiver feed for longer durations. 
• Improving trajectory prediction using machine learning models trained on 
stored samples. 
• Adding filtering by altitude, speed, ICAO address and time range. 
• Adding authentication for multi-user deployment. 
• Deploying the dashboard on a local network or cloud server. 
• Adding automated data-quality reports for missing or stale aircraft fields.
