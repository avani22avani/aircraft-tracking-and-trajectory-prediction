ABSTRACT 
The increasing availability of aircraft surveillance data has created opportunities 
for developing systems that can monitor, analyze, and visualize air traffic in a 
more accessible manner. Automatic Dependent Surveillance–Broadcast (ADS-B) 
is a modern surveillance technology in which aircraft periodically broadcast 
information such as identification, position, altitude, velocity, and heading. These 
broadcasts can be received by ground stations and processed to provide real-time 
awareness of aircraft movements. ADS-B has become an important component of 
contemporary air traffic monitoring due to its ability to provide accurate and 
continuously updated flight information. 
This project focuses on the design and development of an ADS-B Live Aircraft 
Tracking System using Pingstation data as the primary source of surveillance 
information. The objective of the system is to transform raw ADS-B messages 
into meaningful aircraft information that can be monitored, stored, and analyzed 
through an intuitive web-based interface. Instead of relying on specialized 
aviation software, the project provides a lightweight and self-contained platform 
capable of handling aircraft tracking operations using commonly available 
technologies. 
The system receives either live or previously captured ADS-B data streams and 
processes the incoming messages through a custom decoder developed for 
Pingstation binary frames. The decoder extracts relevant aircraft parameters such 
as ICAO aircraft address, callsign, latitude, longitude, altitude, speed, heading, 
and timestamp information. After decoding, the data is validated and normalized 
to ensure consistency across different message types and transmission intervals. 
This processed information is then stored in a structured database for efficient 
retrieval and historical analysis. 
The backend of the application is implemented using Python and Flask, providing 
APIs and services responsible for data ingestion, processing, storage, and 
communication with the frontend. SQLite is used as the primary local database for 
maintaining aircraft records and trajectory history, while CSV and Excel export 
functionalities are incorporated to support external analysis and reporting. These

For visualization, the project employs a browser-based dashboard integrated with

trajectory paths. Recent trajectory points are preserved to provide a visual 
representation of flight routes, improving situational awareness and enabling users 
to understand aircraft movement over time. The system also supports prediction-

A key focus of the project is simplicity, portability, and practical usability. The 
architecture is designed to operate efficiently on standard computing systems 
without requiring complex infrastructure. By combining data acquisition, message 
decoding, storage, export capabilities, and map-based visualization into a single 
platform, the project demonstrates a complete surveillance data processing 
pipeline. The developed system successfully converts low-level ADS-B 
transmissions into human-readable operational information that can be used for 
educational purposes, aviation research, flight trajectory analysis, and surveillance 
system studies. 
Overall, the project highlights the practical application of web technologies, 
database systems, and data processing techniques in the aviation domain. It 
provides a functional framework for aircraft monitoring while offering 
opportunities for future enhancements such as advanced trajectory prediction, 
anomaly detection, integration with additional ADS-B receivers, and large-scale 
cloud-based deployment.

1. OBJECTIVE 
The objective of this project is to design and implement a live ADS-B aircraft 
tracking system that can convert Pingstation raw data into useful aircraft 
information. Raw surveillance messages are not directly suitable for a user 
because they contain encoded binary fields and may arrive in repeated, incomplete 
or stale forms. The project therefore focuses on decoding, cleaning, storing and 
displaying this data through a simple web-based interface. 
The main goals of the project are listed below. 
• Decode useful aircraft information such as ICAO address, callsign, latitude, 
longitude, altitude, heading and speed from Pingstation data. 
• Normalize values into consistent units so that they can be stored and displayed 
without ambiguity. 
• Provide a live browser dashboard that shows aircraft positions, route traces 
and selected aircraft details. 
• Maintain local historical trajectory data for analysis, training data preparation 
and later prediction work. 
• Export aircraft and trajectory data in common formats such as CSV and Excel. 
2. REQUIREMENT ANALYSIS (SRS) 
2.1 Introduction 
The ADS-B tracker is a software system for receiving or replaying aircraft 
surveillance data, converting it into structured records and presenting it to the user 
in near real time. ADS-B is widely used in aviation surveillance because aircraft 
broadcast their identity and state information, including position and movement 
data [1]. The developed system is not a replacement for certified air traffic control 
systems; it is a project-level monitoring and data-logging application for 
understanding and working with ADS-B data. 
2.2 Scope 
• Data input through captured Pingstation log replay and optional live TCP 
stream mode. 
• Frame-level parsing and field extraction from Pingstation messages.

3. REQUIREMENT SPECIFICATION 
3.1 System Inputs 
The system accepts Pingstation data in two modes. In simulation mode, captured 
hex log data is replayed from a local file so that the tracker can be tested without 
live receiver hardware. In live mode, the receiver listens on a configured host and 
port and decodes incoming stream data. Environment variables are used to switch 
modes and configure paths, ports and logging behavior. 
3.2 System Outputs 
• Live aircraft JSON returned by the /api/aircraft endpoint. 
• Latest matrix-style aircraft records from /api/training/matrix. 
• Trajectory history through /api/training/trajectory and CSV export through 
/api/training/trajectory/export. 
• Daily trajectory CSV files under logs/training_csv. 
• ICAO-wise Excel workbooks and a master ICAO workbook. 
• Dashboard visualization using map markers, aircraft list, route panel and 
altitude chart.

5.2 Decoder and Preprocessing 
The decoder reads complete frames from the buffer, extracts fields such as ICAO 
address, callsign, altitude, ground speed, heading, latitude and longitude, and 
maintains an aircraft state snapshot. The preprocessor then ensures values use 
consistent units: altitude in millimetres, speed in centimetres per second and 
heading in degrees multiplied by 100. 
5.3 Storage and Export 
The storage layer writes meaningful trajectory samples instead of saving every 
repeated value. This reduces duplication while retaining useful movement 
information. It also writes CSV files and ICAO-wise Excel workbooks so that the 
data can be reviewed outside the dashboard. 
5.4 User Interface 
The dashboard uses Leaflet for map visualization and Chart.js for the altitude 
chart. Aircraft markers show callsigns and heading direction, while the lower 
panel displays selected aircraft details, route estimate and altitude history. The 
interface is intentionally compact so that tracking information remains visible on 
one screen. 
5.5 Error Handling and Data Quality 
The implementation includes several small safeguards to improve data quality. 
The data source filters records with zero latitude and longitude, the decoder 
ignores incomplete or invalid frames, and the preprocessor applies default values 
when fields are missing. The storage layer uses thresholds for time, distance, 
altitude, heading and speed changes so that the database does not fill with repeated 
identical samples.

def _clean_records(records): 
    filtered = [row for row in records if _is_useful_record(row)] 
    by_callsign = {} 
 
    for row in filtered: 
        callsign = str(row.get("callsign", "")).strip().upper() 
        icao = str(row.get("icaoAddress", "")).strip().upper() 
        key = icao if icao and icao != "UNKNOWN" else callsign 
        if not key: 
            continue 
 
        current = by_callsign.get(key) 
        if current is None: 
            by_callsign[key] = row 
            continue 
 
        def score(rec): 
            lat = float(rec.get("latDD", 0) or 0) 
            lon = float(rec.get("lonDD", 0) or 0) 
            altitude = float(rec.get("altitudeMM", 0) or 0) 
            speed = float(rec.get("horVelocityCMS", 0) or 0) 
            heading = float(rec.get("headingDE2", 0) or 0) 
            squawk = int(rec.get("squawk", 0) or 0) 
            frame_len = int(rec.get("frameLength", 0) or 0) 
            coord_score = 100 if (lat != 0 and lon != 0) else 0 
            altitude_score = 10 if altitude > 0 else 0 
            speed_score = 5 if speed > 0 else 0 
            heading_score = 5 if heading > 0 else 0 
            squawk_score = 2 if squawk > 0 else 0

        if score(row) >= score(current): 
            by_callsign[key] = row

    def split_frames(self, buffer_bytes): 
        """ 
        Splits a byte buffer into complete frames using the first byte as 
frame length. 
        Returns (frames, remainder). 
        """ 
        frames = [] 
        idx = 0 
        total = len(buffer_bytes) 
 
        while idx < total: 
            frame_len = buffer_bytes[idx] 
 
            # Discard obvious noise and re-sync. 
            if frame_len < 10 or frame_len > 120: 
                idx += 1 
                continue 
 
            end_idx = idx + frame_len 
            if end_idx > total: 
                break 
 
            frames.append(buffer_bytes[idx:end_idx]) 
            idx = end_idx 
 
        return frames, buffer_bytes[idx:]

def _haversine_m(lat1, lon1, lat2, lon2): 
    r = 6371000.0 
    p1 = math.radians(lat1) 
    p2 = math.radians(lat2) 
    dlat = math.radians(lat2 - lat1) 
    dlon = math.radians(lon2 - lon1) 
    a = math.sin(dlat / 2) ** 2 + math.cos(p1) * math.cos(p2) * math.sin(dlon 
/ 2) ** 2 
    return 2 * r * math.atan2(math.sqrt(a), math.sqrt(1 - a)) 
 
 
def _bearing_deg(lat1, lon1, lat2, lon2): 
    p1 = math.radians(lat1) 
    p2 = math.radians(lat2) 
    dlon = math.radians(lon2 - lon1) 
    y = math.sin(dlon) * math.cos(p2) 
    x = math.cos(p1) * math.sin(p2) - math.sin(p1) * math.cos(p2) * 
math.cos(dlon) 
    deg = (math.degrees(math.atan2(y, x)) + 360.0) % 360.0 
    return deg

    def _fit_linear_regression_1d(self, xs, ys): 
        n = len(xs) 
        if n < 2: 
            return None 
        x_mean = sum(xs) / n 
        y_mean = sum(ys) / n 
        sxx = 0.0 
        sxy = 0.0 
        for x, y in zip(xs, ys): 
            dx = x - x_mean 
            sxx += dx * dx 
            sxy += dx * (y - y_mean) 
        if sxx <= 0.0: 
            return None 
        b = sxy / sxx 
        a = y_mean - b * x_mean 
        return a, b

APPENDIX G: ALGORITHM SELECTION AND COMPARISON
G.1 Algorithm Used in the Project
The implemented predictor uses sliding-window ordinary least-squares linear regression. For each
aircraft, the latest stored samples are ordered by time. Separate straight lines are fitted for latitude,
longitude and altitude: value(t) = a + bt. The fitted lines are evaluated at the last sample time plus the
number of seconds for which the aircraft has been absent from the current feed.
Implemented constraints
•
Input window: up to the latest 20 stored trajectory points; at least 4 valid points are required.
•
Prediction condition: the aircraft must have been observed in the current session but be absent from the
current live/replay snapshot.
•
Prediction horizon: 1-180 seconds with the current configuration; older records are not displayed as
predictions.
•
Fallback: constant speed, heading and vertical rate are used when regression cannot be fitted.
•
Safety against feedback: predicted rows are output-only and are not written back into the training tables.
G.2 Why This Method Was Selected
For a local academic tracker, this method provides a useful balance: it is understandable, deterministic,
fast enough to run during every API refresh, and able to smooth small variations across several
observations. It needs no offline training dataset or GPU. Its main limitation is that a straight-line trend
cannot model a sharp turn or a prolonged outage, which is why the prediction age is deliberately
capped and the interface visually distinguishes predicted data from live data.
